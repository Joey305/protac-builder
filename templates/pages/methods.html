PROTAC Builder Methods

PROTAC Builder is a component assembly and workflow handoff tool. It helps users turn warheads, linkers, and E3 recruiters into candidate degrader structures while keeping component boundaries, attachment atoms, and downstream-ready representations explicit.

The methodological role of the builder is not to serve as a complete biological prediction engine. Instead, it supports disciplined candidate preparation so downstream modeling, reporting, and experimental planning can be more reproducible.

Design philosophy

Component-plus-geometry

The workflow treats PROTAC design as component assembly constrained by geometry, not as simple concatenation of two ligands and a spacer.

Explicit boundaries

Warhead, linker, and recruiter boundaries are preserved so downstream interpretation does not lose track of where each component begins and ends.

Explicit attachment atoms

Attachment atoms and exit vectors are treated as first-class design choices because wrong anchors can invalidate otherwise attractive chemistry.

Hypothesis framing

Assembled candidates are treated as hypotheses that need descriptor review, structural analysis, and experimental follow-up.

The central methodological assumption: cleaner component representation makes downstream modeling and experimental planning more reproducible.

Component assembly workflow

  1. Select or import a target-binding warhead.
  2. Select or import an E3 recruiter.
  3. Choose or enumerate linkers.
  4. Define attachment atoms and anchor logic.
  5. Assemble candidate molecules.
  6. Inspect the resulting chemical representation.
  7. Export or hand off candidates to downstream workflows.
  8. Evaluate with modeling and experiments.

Warhead methodology

The warhead is the target-binding component. Methodologically, the builder assumes warhead choice should be as structure-aware as possible: preserve target binding, prefer known or credible bound pose context, and identify a plausible attachment atom that does not obviously destroy key interactions.

  • Bound pose and solvent exposure should guide modification-site choice.
  • Warhead Hunter can support upstream inspection of target-bound ligands and candidate modification atoms.
  • Warhead selection should preserve target engagement rather than only maximize abstract modularity.

Linker methodology

Linkers are chosen to test bridgeability hypotheses. The workflow does not treat them as passive spacers. Instead, it assumes linker choices affect reach, flexibility, rigidity, polarity, rotatable-bond burden, and the geometric feasibility of a ternary arrangement.

  • Flexible and rigid alternatives should both be considered where appropriate.
  • Length, polarity, and attachment chemistry should be documented rather than guessed implicitly.
  • Bridgeability should be reviewed before expensive downstream modeling begins.

E3 recruiter methodology

The recruiter defines ligase-side binding and attachment geometry. The method assumes recruiter choice should consider bound pose, scaffold context, solvent exposure, and when possible the biological context of the recruited ligase rather than defaulting blindly to one familiar example.

  • E3 choice influences ternary geometry and downstream compatibility.
  • Recruiter-side attachment vectors deserve the same care as warhead-side attachment vectors.
  • E3 Ligandalyzer supports upstream recruiter inspection before assembly.

Attachment atoms and exit vectors

Attachment atoms are where the linker connects. Exit vectors describe how the linker leaves the warhead and the recruiter. This part of the method is critical because a 2D-valid assembly can still be a poor 3D hypothesis if the anchor choices point into steric clashes or destroy key interactions.

Is the atom solvent-exposed?
Does it preserve key binding interactions?
Does it point toward plausible partner-protein space?
Are alternate attachment atoms worth testing?

Query-parameter launch workflows

Implemented query parameters create reproducible entry points for examples, documentation, teaching, and scripted workflows. Current examples include:

  • /builder?ligand=DR7
  • /builder?ligase=CRBN_Y70
  • /builder?ligase=VHL_3JS
  • /builder?smiles=CCCCC

These routes help document starting conditions more explicitly. Invalid or missing IDs should fail clearly or fall back safely depending on the implemented path.

API and batch methodology

API Builder and the public route surface support scriptable workflows where implemented. Methodologically, batch workflows should preserve component IDs, custom SMILES where relevant, attachment atoms, linker identifiers, query parameters, and output metadata so runs can be reproduced later.

Validation and interpretation

Builder output is a hypothesis. Downstream validation can include descriptor review, bridgeability checks, ternary modeling, molecular dynamics, ML re-ranking, and experimental degradation assays. No single computational score proves activity.

  • DC50, Dmax, hook effect, selectivity, and target engagement remain experimental concepts.
  • Computational signals can rank or explain, but not replace biological validation.
  • Interpretation should remain aligned with what the current workflow actually measures.

Current limitations

  • Not a guarantee of degradation.
  • Not a complete component universe.
  • Not all query parameters or exports may be supported in every deployment.
  • Custom SMILES still require user validation.
  • 2D-valid assembly does not guarantee 3D bridgeability.
  • Downstream modeling and experiments remain necessary.
  • Data and features may change as the platform evolves.
